# SceneFinder 장면 검색 구조 정리: 기존 구조 → VLM 설명문 검색 추가

SceneFinder는 YouTube 영상에서 「달걀말이가 찢어진 장면」처럼 말로 찾고 싶은 장면을 입력하면, 그 장면이 나오는 구간(몇 초~몇 초)을 찾아 주는 서비스입니다.
이 문서는 검색 구조를 어떻게 바꿨는지, 왜 바꿨는지, 얼마나 좋아졌는지를 정리합니다.

**읽는 법**

- 성능 수치는 모두 `docs/experiments/`의 실험 문서에 있는 값이고, 숫자 옆 `[번호]`가 출처입니다(맨 아래 「출처」).
- 「2초마다 프레임 1장」 같은 **설정값은 코드에서 확인**했고, 그 경우 `(코드: 파일 경로)`로 표시했습니다.
- 코드나 문서로 확인하지 못한 내용은 **확인 안 됨**으로 표시했습니다.
- 처음 나오는 용어에는 한 줄 설명을 붙였고, 맨 아래 「용어 정리」에 모아 두었습니다.

---

## 1. 기존 구조

영상은 사용자가 처음 검색할 때 한 번 분석하고(분석이 끝난 상태 = **INDEXED**), 그 뒤 검색은 분석 결과로 합니다.

```
[분석] 영상을 처음 검색할 때 1번
  YouTube 영상 다운로드
    → Whisper small로 말소리를 자막으로 받아쓰기
    → 한국어 자막이 있나? (문장 3개 이상, 30자 이상)
        ├─ 있음 → 자막 파일 저장 → INDEXED
        └─ 없음 → CLIP으로 2초마다 화면 특징(feature) 저장 → INDEXED
    → 영상 파일 삭제

[검색] 질의가 들어올 때마다
  이 영상에 한국어 자막이 있나?
    ├─ 있음 → 자막을 연속 1~3문장씩 묶은 「창」을 만듦
    │        → MiniLM으로 창과 질의를 벡터로 바꿔 코사인 유사도 비교
    │        → 점수 높은 창 = 결과 구간 (시작 2초 앞당김, 최소 6초)
    └─ 없음 → NLLB로 질의를 한국어 → 영어 번역
             → Moment-DETR가 화면 특징에서 구간 후보를 냄
             → 결과 구간
```

- **Whisper**: 말소리를 글자로 받아쓰는 음성 인식 모델. 기존 서비스 기본값은 `small`이었습니다[3].
- **MiniLM**: 문장을 숫자 벡터(임베딩)로 바꾸는 작은 모델. 서비스는 AI-Hub 한국어 데이터로 추가 학습한 것을 씁니다[7].
- **코사인 유사도**: 두 벡터가 얼마나 같은 방향인지(=의미가 비슷한지)를 −1~1로 나타낸 값.
- **Moment-DETR**: 영어 문장을 받아 영상에서 해당 구간을 찾아 주는 모델. 영어 데이터(QVHighlights)로 학습됐습니다[1].
- **CLIP**: 이미지와 글을 같은 벡터 공간에 놓는 모델. 여기서는 2초마다 화면 특징을 뽑는 데 씁니다.
- 자막 판정 기준(문장 3개·30자)과 구간 보정(2초·6초)은 `(코드: backend/services/subtitles.py, backend/services/search_api.py)`. 화면 특징 2초 간격은 [1]의 실험 설정과 같습니다[1].
- 번역 모델은 `.env`에 따로 지정하지 않으면 `facebook/nllb-200-distilled-600M` `(코드: backend/services/translate.py)`. 지금 서버는 따로 지정하지 않았습니다.
- 자막 창 임베딩은 저장하지 않고 **검색할 때마다 다시 계산**했습니다[4].

## 2. 기존 구조의 문제점

### 2-1. 화면에만 보이는 장면은 거의 못 찾음

질의를 두 종류로 나눴습니다. **S** = 말로도 설명되는 장면, **V** = 말로는 안 나오고 화면에만 보이는 장면.

| 방식 (평가셋 v2, 질의 90개) | S IoU≥0.3 | V IoU≥0.3 | 전체 IoU≥0.3 |
|---|---|---|---|
| 자막 검색 (Whisper small + MiniLM) | 27% (8/30) | 3% (2/60) | 11% (10/90) |
| NLLB 번역 + Moment-DETR | 10% (3/30) | 5% (3/60) | 7% (6/90) |
| 무작위로 구간을 고를 때 (기댓값) | 3% | 2% | 3% |

출처 [2]. **IoU**는 찾은 구간과 정답 구간이 겹치는 정도(0~1)이고, 「IoU≥0.3」은 30% 이상 겹친 비율입니다.

- 자막 검색은 자막에 그 장면을 말한 문장이 없으면 찾을 수 없습니다. V에서 3%였습니다[2].
- 자막이 없는 영상의 Moment-DETR 경로도 무작위보다 조금 나은 수준(전체 7%)이었습니다[2].

### 2-2. 자막이 없는 영상의 경로(번역 + Moment-DETR)가 약함

- **번역 오류**: 질의 20개 중 NLLB 번역이 의미를 틀린 것이 10개(opus-mt는 3개)였습니다[1]. 예: 「노란 도마 위에 썰어둔 두부」 → "two couples lying on a yellow dome"[1].
- **번역을 고쳐도 안 오름**: 번역이 더 나은 opus-mt로 바꿔도 Moment-DETR 검색은 좋아지지 않았습니다. 병목은 번역보다 Moment-DETR 쪽입니다[1].
- **구간이 너무 김**: Moment-DETR는 1위 구간 길이가 중앙값 32초로, 정답보다 훨씬 길어 IoU가 낮게 나왔습니다[2].

### 2-3. 자막 품질

- Whisper small은 오인식·누락이 있었습니다. 예: 「소음을 상쇄」를 「상세」로 받아씀, 말 없는 450초를 한 문장으로 합침[2].
- 같은 내용을 다른 시점에 말하는 경우(조명 이야기는 87초, 켜는 장면은 309초)에도 틀렸습니다[2].

## 3. 평가 방법

| 항목 | 내용 |
|---|---|
| 영상 | 서비스에서 분석했던 YouTube 영상 **12개** (2:40~15:01, 요리·리뷰·스포츠·강의·브이로그·먹방·음악). 말이 거의 없는 영상 5개 포함[2] |
| 질의 | **118개** = dev 60 + test 58[6]. 영상에 없는 장면(정답 없음) 질의 12개는 따로 있고 아직 평가하지 않음[2] |
| 질의 종류 | S(말로도 설명되는 장면) / V(화면에만 보이는 장면). S는 다시 **말 내용**(소리만 들어도 찾을 수 있음, 예: 「배터리 수명 늘리는 방법 설명」)과 **화면 묘사**(소리를 꺼도 찾을 수 있음, 예: 「러그 까는 장면」)로 나눔[2] |
| dev / test | 영상 단위로 6개씩 나눔. **설정은 dev 결과로만 정하고, test는 최종 확인에만 씀**. 나눌 때는 결과를 보지 않고 분야·말 양·길이만 맞춤[2] |
| 질의 작성 | **AI가 초안을 쓰고 사람이 검수**함. 2~3초 간격 프레임과 자막을 보고 질의·정답 구간을 만들고, 경계는 프레임으로 맞춤[2]. 처음 90개는 검수에서 고친 것이 0개였음[2] |
| 지표 | IoU≥0.3, IoU≥0.5, R@3, 시작 ±5초 (아래) |
| 잡음 수준 | 설명문을 다시 만드는 것만으로 dev 47개 중 IoU≥0.3·R@3이 **최대 3개** 움직임 → **±3개 이내 차이는 의미 있게 보지 않음**[5][4] |

지표 설명

- **IoU≥0.3 / IoU≥0.5**: 1위 구간이 정답과 30% / 50% 이상 겹친 질의 수.
- **R@3**: 상위 3개 구간 중 하나라도 IoU≥0.3인 질의 수. 겹치는 후보는 하나로 셈(NMS)[6].
- **시작 ±5초**: 1위 구간의 시작이 정답 시작에서 5초 안인 질의 수[2].
- **NMS**: 앞 순위 구간과 많이(IoU 0.5 이상) 겹치는 아래 순위 구간을 같은 것으로 보고 빼는 처리.

## 4. 바꾼 구조

바뀐 점은 네 가지입니다.

1. **Whisper 모델 교체:** `small` → `large-v3-turbo` `(코드: backend/services/subtitles.py 기본값)`
2. **설명문 생성 추가:** 화면을 보고 문장으로 설명하는 VLM(Qwen3-VL-4B)으로 2초마다 화면 설명문을 만듭니다.
3. **설명문 검색 추가:** 설명문은 다른 임베딩 모델(multilingual-e5-large)로 검색합니다.
4. **두 검색 결과 결합:** 자막 검색과 설명문 검색의 결과를 합칩니다.

- **VLM**(Vision-Language Model): 이미지를 보고 글로 설명할 수 있는 모델.
- **e5-large**: MiniLM보다 큰 다국어 임베딩 모델. 질의 앞에 `query: `, 문서 앞에 `passage: `를 붙여 씁니다.
- 기능 스위치는 `CAPTION_SEARCH_ENABLED`입니다. 코드 기본값은 꺼짐이고, 서버 설정에서만 켰습니다[6].

### 4-1. 분석 흐름 (CAPTION_SEARCH_ENABLED=1)

```
[분석] 영상을 처음 검색할 때 1번
  YouTube 영상 다운로드
    → Whisper large-v3-turbo로 자막 만들기
    → 한국어 자막이 있나?
        ├─ 있음 → 자막 파일 저장
        └─ 없음 → CLIP 화면 특징 저장 (기존과 같음)
    → INDEXED  ← 여기서부터 바로 검색 가능 (기존과 같은 시점)
    → 설명문 대기열에 넣고 분석 작업은 끝

[설명문] 작업 스레드 1개가 대기열을 차례로 처리 (분석과 따로)
  2초마다 가운데 프레임 1장 (긴 변 640px)
    → Qwen3-VL-4B가 8장씩 묶어 한국어 한 문장으로 설명 (화면 글자도 적게 함)
    → 연속 1~3개 설명문을 묶은 창을 e5-large로 임베딩해 파일 저장
    → 설명문 상태 READY
    → 영상 파일 삭제
```

- 프레임 간격(2초)·크기(긴 변 640px)·묶음(8장)·프롬프트 `(코드: backend/services/captions.py)`. 실험과 같은 설정입니다[2][5].
- 대기열 규칙 `(코드: backend/services/captions.py)`
  - 동시에 1개만 생성하고, 기다리는 작업은 최대 5개입니다(`CAPTION_QUEUE_MAX`).
  - 사용자가 직접 연 영상은 대기열 맨 앞으로 갑니다.
  - 대기열이 가득 차면 설명문 상태를 PENDING으로 두고 영상 파일은 바로 지웁니다. 나중에 다시 분석하면 생성됩니다.
- 설명문 모델은 10분 동안 안 쓰면 GPU에서 내립니다. Whisper가 GPU 메모리 부족을 만나면 설명문 모델을 먼저 내리고 Whisper를 다시 시도합니다 `(코드: backend/services/captions.py, subtitles.py)`.
- 처음에는 분석 작업 안에서 설명문이 끝날 때까지 기다리게 만들었습니다. 그랬더니 여러 영상을 한 번에 분석할 때 뒤 영상의 INDEXED가 앞 영상 설명문만큼 늦어져서, 지금처럼 따로 돌게 고쳤습니다[6].
- 화면에는 설명문을 만드는 중이면 「화면 분석 중」, 대기 중이면 「화면 분석 대기」가 표시됩니다 `(코드: frontend/src/components/AnalysisStatusBadge.tsx)`.

### 4-2. 검색 경로: 영상 상태별 (CAPTION_SEARCH_ENABLED=1)

`backend/services/search_api.py`의 `predict_moments`와 `backend/services/captions.py`의 `fused_search` 기준입니다.

| 한국어 자막 | 설명문 | 쓰는 것 | 결과를 만드는 방법 |
|---|---|---|---|
| 있음 | READY | **MiniLM(자막) + e5(설명문)** | 아래 「결합」 |
| 있음 | READY 아님 | MiniLM(자막)만 | 기존 자막 검색과 같음 |
| 없음 | READY | **e5(설명문)만** | 설명문 점수 순서대로. **Moment-DETR는 쓰지 않음** |
| 없음 | READY 아님 | NLLB 번역 + Moment-DETR | 기존과 같음. 화면 특징 파일도 없으면 결과 없음 |

- **「한국어 자막 있음」**: 자막 파일의 언어가 `ko`이고 문장이 남아 있는 경우입니다. 문장 3개 미만이거나 30자 미만이면 자막을 비워 「없음」이 됩니다.
- **「설명문 READY」(검색 쪽 판단)**: DB 상태가 아니라 **이 서버에 설명문 파일과 임베딩 파일이 있고, 만든 임베딩 모델이 지금 설정과 같으면** 결합 검색을 씁니다(`load_index`). 만드는 중(PROCESSING)·대기(PENDING)·실패(FAILED)면 파일이 없으므로 기존 경로로 갑니다.
- 결합 검색 중 오류가 나면 기존 경로로 대신 검색합니다.
- 기능이 꺼져 있으면(`=0`) 영상 상태와 상관없이 검색 경로는 1장의 기존 구조와 같습니다(Whisper만 large-v3-turbo).

**결합 (한국어 자막 있음 + 설명문 READY)**

```
질의
  ├─ 자막 쪽: 자막 1~3문장 창 × MiniLM → 창마다 코사인 점수
  │          (창 임베딩은 파일로 저장해 다시 씀)
  └─ 설명문 쪽: 설명문 1~3개 창 × e5-large → 창마다 코사인 점수

1위 고르기 (기본 규칙 zscore_max)
  각 쪽의 모든 창 점수를 그 영상 안에서 z-score로 바꿈
    → 자막 1위의 z와 설명문 1위의 z 중 큰 쪽이 전체 1위
  단, 한쪽이라도 창이 5개 미만이거나 점수 퍼짐(표준편차)이 0.01 미만이면
    → z-score를 쓰지 않고 자막 1위를 전체 1위로 (subtitle_first)

2위부터
  1위를 낸 쪽부터 자막·설명문을 번갈아 하나씩 채움
  이미 고른 구간과 많이 겹치면(짧은 쪽의 50% 이상) 건너뜀

구간 다듬기
  자막 구간: 시작 2초 앞당김, 최소 6초 (기존과 같음)
  설명문 구간: 앞뒤 2초씩 넓힘
```

- **z-score**: 「이 점수가 그 영상의 평균보다 표준편차 몇 개만큼 높은가」. MiniLM과 e5는 점수 범위가 달라 원점수를 그대로 비교할 수 없어서, 각자 영상 안에서의 상대 위치로 바꿔 비교합니다.
- 결과마다 `source`(`subtitle` / `caption`)가 붙고, 점수는 각 모델의 원래 코사인 값입니다. 그래서 화면은 점수가 아니라 백엔드가 정한 순서로 보여 줍니다 `(코드: frontend/src/services/searchApi.ts)`.
- 기준값 5개·0.01, 확장 2초는 dev 비교 전에 정했습니다 `(코드: backend/services/captions.py, 문서: docs/design/vlm_search.md)`.

## 5. 성능

### 5-1. 단계별 개선

| 단계 | 바꾼 것 | 결과 | 출처 |
|---|---|---|---|
| ① 자막 받아쓰기 | Whisper small → large-v3-turbo | 자막 검색 S IoU≥0.3 **27% → 43%** (8/30 → 13/30, dev 5→7·test 3→6). 자막 생성 시간도 영상 8개 합계 78.7초 → 56.6초 | [2][3] |
| ② 설명문 묶음 처리 | 1장씩 → 8장씩 | 장당 2.29초 → 0.38초 (약 6배 빠름). 검색 결과는 묶음 크기에 따른 일정한 방향 없음(잡음 수준) | [5] |
| ③ 설명문 임베딩 | MiniLM → e5-large | 설명문 검색 V: dev R@3 7 → 13, test IoU≥0.3 6 → 12 · R@3 12 → 17 (잡음 수준 넘음) | [4] |
| (참고) 자막 임베딩 | MiniLM → e5-large | dev 말 내용 S 7 → 11이었지만 test에서는 10 → 11로 재현 안 됨 → **자막은 MiniLM 유지** | [4] |
| ④ 서비스 결합 | 자막만 → 자막 + 설명문 (zscore_max, 확장 2초) | 아래 5-2 | [6] |

①은 dev/test를 나누기 전 질의 90개 전체로 잰 값이라 test도 이미 본 상태였습니다[2].

### 5-2. 서비스 끔 / 켬 (test, 실제 서비스 검색 API로 잼)

결합 후보 3개를 dev에서 비교해 미리 정한 기준을 통과하고 V가 가장 많이 오른 `zscore_max·확장 2초`를 고른 뒤, test에서 **한 번만** 확인했습니다[6].

| 묶음 (test 질의 수) | 끔 IoU≥0.3 | 켬 IoU≥0.3 | 끔 R@3 | 켬 R@3 |
|---|---|---|---|---|
| 전체 (58) | 20 | **28** | 24 | 42 |
| S (31) | 17 | 15 | 19 | 23 |
| ㄴ S 말 내용 (15) | 10 | 8 | 10 | 12 |
| ㄴ S 화면 묘사 (16) | 7 | 7 | 9 | 11 |
| V (27) | 3 | **13** | 5 | **19** |

출처 [6]. 전체 R@3(24 → 42)은 [6]의 S·V 값을 더한 것입니다.

- V는 IoU≥0.3 +10, R@3 +14로 크게 올랐습니다[6].
- S는 IoU≥0.3이 2개 줄었습니다(말 내용에서 2개)[6]. 아래 6장 참고.
- 1위가 설명문인 질의는 58개 중 36개였습니다[6].

## 6. 한계와 다음 단계

### 6-1. 한계

- **S 기준 미달(−2)**
  - dev 비교 전에 「S의 IoU≥0.3은 1개 넘게 줄지 않음, 말 내용 S는 줄지 않음」을 기준으로 정했는데, test에서 S 17 → 15, 말 내용 S 10 → 8로 **둘 다 미달**이었습니다[6].
  - −2는 잡음 수준(±3) 안이고 R@3은 올랐지만, 미리 정한 판정은 「불통과」입니다[6].
  - 그래도 전체 IoU≥0.3 20 → 28, V 3 → 13, S R@3 19 → 23을 근거로 서비스에서 켜기로 결정했습니다[6].
  - 원인: 해설·평가처럼 말로만 나오는 장면을 자막은 맞히는데, 설명문 쪽 z-score가 더 커서 1위를 가져갔습니다. 예: 「네이마르 혼자 골을 만들어냈다는 평가」 IoU 0.69 → 0.00[6].
- **test 두 번째 사용**
  - test는 임베딩 비교에서 한 번, 이번 서비스 비교에서 한 번, 모두 두 번 봤습니다[6][4].
  - 같은 test로 계속 확인하면 test에 맞춰 고르는 위험이 커집니다. 그래서 test 결과를 본 뒤 결합 규칙을 다시 고르지 않았습니다[6].
- **질의 작성 방식**
  - 질의와 정답은 AI 초안을 사람이 검수한 것이고, 처음 90개는 검수에서 고친 것이 0개였습니다[2]. 사람이 처음부터 쓴 질의와 결과가 같을지는 확인 안 됨.
  - 검수자 수: **확인 안 됨** (문서에 없음).
  - 정답 경계는 프레임 기준 대략값입니다[2].
  - 처음 S 질의 30개 중 말 내용 질의가 2개뿐이어서(초안 지침이 화면 묘사형 예시를 줬기 때문), 말 내용 질의를 dev 13·test 15개 추가했습니다[2].
- **질의 수가 적음**
  - 묶음마다 15~33개라 ±3개 차이는 우연일 수 있습니다[4].
  - 정답 없음 질의 12개(영상에 없는 장면을 찾을 때 「없음」이라고 답하는지)는 아직 평가하지 않았습니다[2].
- **결과가 실행마다 조금씩 다름**
  - 같은 영상도 다시 분석하면 Whisper 자막이 조금씩 달라져, test 14개 질의에서 끔 결과가 바뀌었습니다. 그래서 끔·켬은 같은 자막 파일로 비교했습니다[6].
  - 설명문도 묶음 크기에 따라 bf16 계산 오차로 문장이 달라집니다[5].
- **대기열이 가득 찼을 때**: 사용자가 연 영상도 설명문이 PENDING이 됩니다(다시 분석해야 생성)[6].

### 6-2. 다음 할 일

1. **새 test 세트를 만들고**, 말 내용 질의에서 자막을 우선하는 규칙을 검증합니다[6].
2. **정답 없음 질의 12개로** 「결과 없음」 판정 점수 기준을 정합니다[2].
3. **상위 후보 다시 순위 매기기, 또는 상위 몇 개를 함께 보여 주기**: 1위는 틀렸지만 2~3위에 정답이 있는 경우가 많았습니다(설명문 검색 1위 14% vs R@3 32%)[2].
4. **e5-large 추가 학습(fine-tuning)**: 계획만 있고 아직 하지 않았습니다. 학습 데이터도 이 서버에서 찾지 못한 상태입니다[7].
5. **운영 GPU 전체 메모리 사용량 측정**: 지금은 확인 안 됨.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 질의 | 사용자가 입력하는 검색 문장. 예: 「러그 까는 장면」 |
| 구간 | 영상의 시작~끝 시각. 검색 결과는 구간으로 나옴 |
| S / V | S: 말로도 설명되는 장면. V: 말로는 안 나오고 화면에만 보이는 장면 |
| 말 내용 / 화면 묘사 | S를 다시 나눈 것. 말 내용은 소리만 들어도, 화면 묘사는 소리를 꺼도 찾을 수 있는 질의 |
| IoU | 찾은 구간과 정답 구간이 겹친 길이 ÷ 둘을 합친 길이. 0(안 겹침)~1(똑같음) |
| IoU≥0.3 / ≥0.5 | 1위 구간이 정답과 30% / 50% 이상 겹친 질의 수(또는 비율) |
| R@3 | 상위 3개 구간 중 하나라도 IoU≥0.3인 질의 수 |
| 시작 ±5초 | 1위 구간 시작이 정답 시작에서 5초 안인 질의 수 |
| NMS | 많이 겹치는 아래 순위 후보를 같은 것으로 보고 빼는 처리 |
| 잡음 수준 | 같은 실험을 다시 해도 생기는 흔들림. 여기서는 ±3개 |
| dev / test | dev: 설정을 정할 때 보는 데이터. test: 정한 설정을 마지막에 확인만 하는 데이터. 둘을 나눠야 결과에 맞춘 설정을 막을 수 있음 |
| 임베딩 | 문장을 의미가 비슷하면 가까워지도록 숫자 벡터로 바꾼 것 |
| 코사인 유사도 | 두 임베딩이 얼마나 비슷한지를 −1~1로 나타낸 값 |
| z-score | (점수 − 평균) ÷ 표준편차. 점수 범위가 다른 두 모델의 점수를 같은 기준으로 비교하려고 씀 |
| 창 | 연속된 자막 1~3문장(또는 설명문 1~3개)을 묶은 검색 단위 |
| Whisper | 말소리를 글자로 받아쓰는 음성 인식 모델 (small, large-v3-turbo는 크기 이름) |
| MiniLM | 작은 문장 임베딩 모델. 서비스는 한국어 데이터로 추가 학습한 것을 자막 검색에 씀 |
| e5-large (multilingual-e5-large) | MiniLM보다 큰 다국어 문장 임베딩 모델. 설명문 검색에 씀 |
| VLM / Qwen3-VL-4B | 이미지를 보고 글로 설명하는 모델 / 그중 이 서비스가 쓰는 모델 |
| 설명문 (caption) | VLM이 2초마다 프레임 1장을 보고 쓴 한국어 한 문장 |
| CLIP | 이미지와 글을 같은 벡터 공간에 놓는 모델. 화면 특징 추출에 씀 |
| Moment-DETR | 영어 문장으로 영상 구간을 찾는 모델. 자막 없는 영상의 기존 경로 |
| NLLB | 한국어 질의를 영어로 바꾸는 번역 모델 |
| INDEXED | 영상 분석이 끝나 검색할 수 있는 상태 |
| PENDING / PROCESSING / READY / FAILED | 설명문 상태: 대기 / 만드는 중 / 완료 / 실패 |
| bf16 (bfloat16) | 계산을 빠르게 하려고 쓰는 낮은 정밀도 숫자 형식. 작은 계산 오차가 생김 |
| p50 / p95 | 응답 시간의 가운데 값 / 95%가 이보다 빠른 값 |
| fine-tuning (추가 학습) | 이미 학습된 모델을 우리 데이터로 조금 더 학습시키는 것 |
