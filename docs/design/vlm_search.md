# VLM 설명문 검색 설계

화면에만 보이는 장면(V)을 찾기 위해, 자막 검색에 VLM 설명문 검색을 더합니다. 근거 실험은 [eval_v2.md](../experiments/eval_v2.md),
[embedding_compare.md](../experiments/embedding_compare.md), [caption_batch_compare.md](../experiments/caption_batch_compare.md)입니다.

**이 문서의 「미리 정한 값」 절은 dev 비교를 하기 전에 정해 커밋했습니다(2026-10-17).** 결과를 본 뒤 바꾸면 그 사실과 이유를 결과 문서에 적습니다.

## 분석 흐름

1. 영상 받기(또는 로컬 파일) → Whisper 자막 → **INDEXED (이때부터 자막 검색 가능)**
2. 한국어 자막이 없으면 지금처럼 Moment-DETR feature도 만듦
3. `CAPTION_SEARCH_ENABLED=1`이면 설명문 대기열에 넣고 분석 작업은 바로 끝남. 설명문은 **작업 스레드 1개**가 차례로 생성
   - 2초마다 가운데 프레임 1장(긴 변 640px)을 Qwen3-VL-4B로 설명(화면 글자 포함 프롬프트, greedy, 최대 80토큰, 8장 묶음)
   - 연속 1~3개 설명문 창을 multilingual-e5-large로 임베딩(`passage: `)해 파일로 저장
4. 설명문이 끝나면 작업 스레드가 영상 파일 삭제(YouTube에서 받은 경우만, 로컬 파일은 남김). 대기열에 못 들어가면 분석 작업이 바로 삭제

(처음 구현은 분석 작업 안에서 설명문이 끝날 때까지 기다렸는데, 한 검색 요청의 여러 영상 분석이 차례로 실행되어
다음 영상의 INDEXED가 앞 영상 설명문만큼 늦어졌음. 2026-10-17 수정, [vlm_service_compare.md](../experiments/vlm_service_compare.md))

## 대기열

- 설명문 생성은 **동시에 1개**만. 검색·Whisper가 쓰는 잠금(`_AI_LOCK`)과 따로 둬서 설명문 생성 중에도 검색이 막히지 않음
- 기다리는 작업은 **최대 `CAPTION_QUEUE_MAX`개(기본 5)**. 넘치면 `caption_status=PENDING`(오류 메시지에 이유)으로 두고 영상 파일은 평소처럼 지움.
  나중에 다시 분석(`force`)하면 생성
- 사용자가 직접 연 영상(단일 검색 `POST /api/search`, 로컬 분석 API)은 **대기열 맨 앞**. 이미 대기 중인 영상을 단일 검색하면 앞으로 옮김
- 대기열이 바뀔 때마다 대기 수와 **설명문 때문에 디스크에 남아 있는 영상 파일 총량**을 로그로 남김
- 서버가 재시작되면 진행 중(PROCESSING)이던 영상은 FAILED, 대기 중이던 영상은 PENDING(다시 분석하면 생성)

## 검색 (설명문이 READY인 영상만, 아니면 지금 서비스와 같음)

- 자막: 지금과 같은 fine-tuned MiniLM, 연속 1~3문장 창, 서비스 구간 보정(시작 2초 앞당김, 최소 6초). 창 임베딩은 파일로 저장해 다시 씀
- 설명문: e5-large(`query: ` 질의), 1위 창 구간을 앞뒤 `CAPTION_SPAN_EXPAND_SEC`초(기본 2) 넓힘
- 결합(`CAPTION_FUSION`)
  - `zscore_max`(기본): 영상 하나 안에서 출처별로 모든 창의 점수를 z-score로 바꾼 뒤, 1위 후보 둘 중 z가 큰 쪽이 1위
  - `subtitle_first`: 자막이 있으면 자막 1위, 없으면 설명문 1위
  - 2위부터는 두 출처를 번갈아 채우고 겹치는 구간(짧은 쪽의 50% 이상)은 뺌
- 한국어 자막이 없는 영상: 설명문 검색만 씀(Moment-DETR 대신)
- 응답의 결과마다 `source`(`subtitle` / `caption`), 점수는 각 모델의 원래 코사인 유사도

## 미리 정한 값 (dev 비교 전)

| 항목 | 값 | 이유 |
|---|---|---|
| z-score를 쓰지 않는 조건 | 한 출처의 창이 **5개 미만**이거나 창 점수의 표준편차가 **0.01 미만** | 창이 적으면 평균·표준편차가 불안정. 실험에서 본 코사인 점수의 퍼짐(창들의 표준편차 대략 0.03~0.08)보다 충분히 작은 값을 「매우 작음」으로 봄 |
| 그때 쓰는 규칙 | `subtitle_first`와 같음 (원점수 순위로 각 출처 1위를 정하고, 자막이 있으면 자막 1위) | 두 모델의 원점수는 직접 비교할 수 없으므로, 지금 서비스의 자막 결과를 지키는 쪽 |
| 설명문 구간 확장 | 앞뒤 2초 | eval_v2에서 확장 없이 1위 구간이 2초라 IoU가 낮았음. 탐색적 결과라 dev 비교에서 0초와 함께 봄 |
| 설명문 묶음 크기 | 8 | caption_batch_compare.md (1·4·8 사이 방향 없음, 8이 가장 빠름) |

## 검증 계획 (구현 후)

- 실제 서비스 검색 경로(`POST /api/search`)로 dev 검수 질의 60개(S 27 = 말 내용 15 + 화면 묘사 12, V 33)를 「끔」(지금 서비스)과 「켬」으로 비교
- **판정 기준 (모두 만족)**
  - S: IoU ≥ 0.3과 R@3이 각각 **1개 넘게 줄지 않음**. 말 내용 S는 줄지 않음. 1위가 바뀐 S 질의는 목록으로 확인
  - V: IoU ≥ 0.3 또는 R@3이 **4개 이상 늘어남**(잡음 수준 ±3개를 넘음)
  - 검색 응답 시간 p95 증가 200ms 이내, 「검색 가능」(INDEXED)이 끔 대비 늦어지지 않음, 설명문 실패 시 자막 검색 정상
- 결합 후보(`zscore_max` 확장 2초 / `zscore_max` 확장 0초 / `subtitle_first`) 중 dev에서 기준을 통과하고 V가 가장 많이 오른 것을 골라 **test로 한 번** 확인.
  test는 임베딩 비교에서 이미 한 번 썼으므로 이번이 **두 번째 사용**임을 결과 문서에 적음
- 질의는 **AI 초안을 사람이 검수**한 것임을 결과 문서에 적음
