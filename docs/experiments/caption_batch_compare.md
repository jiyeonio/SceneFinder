# 설명문 묶음 크기 비교 (1 / 4 / 8장, dev)

Qwen3-VL-4B 설명문을 묶음 크기만 바꿔 만들고 dev 영상 6개(eggroll_paik, room_vlog, ag_final, steak_camp, airpods_fake, mukbang_chicken)의 질의 47개로 비교했습니다. 자막·CLIP feature·라벨은 모두 같습니다. 묶음 1은 [eval_v2.md](eval_v2.md)의 처음 결과, 묶음 8은 지금 기본값입니다.

## 원인

같은 프레임인데 묶음 크기에 따라 설명문이 달라지는 원인을 확인했습니다(eggroll_paik 8장으로 실험).

| 확인 | 결과 |
|---|---|
| 생성 방식 | 모델 기본 설정은 `do_sample=True`(temperature 0.7)지만 captions.py가 `do_sample=False`를 넘겨 **greedy**. 같은 묶음 크기로 두 번 돌리면 8/8 같음 |
| 패딩 | 왼쪽 패딩으로 설정돼 있으나, 같은 영상의 프레임은 크기(640×360)와 프롬프트가 같아 **패딩이 생기지 않음** (8장 모두 296토큰) |
| 다른 이미지의 영향 | 같은 그림 8장을 묶어도 vision 임베딩이 혼자일 때와 다름 → 다른 이미지가 섞여 생기는 문제가 아님 |
| 정밀도 | 혼자 vs 8장 묶음의 vision 임베딩 상대 차이: **bfloat16 평균 4.9%(최대 7.1%), float32 0.001%** |

**결론:** 버그가 아니라 bfloat16 계산 오차입니다. 묶음 크기에 따라 GPU 연산 방식이 달라지고, bf16에서는 그 차이가 vision 임베딩에서 약 5%까지 벌어집니다. greedy 생성은 앞 단어 하나만 달라져도 뒤 문장이 갈라지므로 설명문이 달라집니다. 1장씩 처리한 결과도 같은 크기의 bf16 오차를 가진 하나의 결과일 뿐 '정답'은 아닙니다. 고칠 설정(패딩·샘플링)은 없었고, 차이를 없애려면 vision 부분을 float32로 돌려야 합니다(속도·메모리 비용, 이번에는 적용 안 함).

## 해석

1. **묶음 4와 8은 묶음 1과 같은 정도로 다릅니다(같은 설명문 37%·38%, 글자 유사도 0.85).** 묶음을 줄인다고 1장씩 처리에 가까워지지 않습니다. bf16 오차는 묶음 크기가 1이 아니면 비슷하게 생깁니다.
2. **검색 결과에 묶음 크기에 따른 일정한 방향이 없습니다.** 묶음 4가 1과 8 사이에 오지 않고, 지표에 따라 8보다 낮기도 합니다. 차이는 dev 47개 중 1~4개로, 설명문을 다시 만들 때 생기는 흔들림(잡음) 수준으로 봅니다. 묶음 1이 조금씩 높지만 이 데이터로는 '1장씩이 더 낫다'고 말할 수 없습니다.
3. **권장: 묶음 8 유지.** 1장씩보다 약 6배 빠르고(장당 2.29초 → 0.38초) GPU 메모리 차이는 0.5GiB입니다. 묶음 4는 8보다 느리고 결과가 나은 것도 아닙니다.
4. **앞으로 비교할 때의 기준:** 설명문을 다시 만드는 것만으로 (e) IoU ≥ 0.3이 dev 47개 중 최대 3개, R@3이 최대 3개 움직입니다. 설명문을 새로 만드는 설정 비교(프롬프트·모델 등)에서는 이보다 큰 차이만 의미 있게 봐야 합니다. 같은 설명문 파일을 쓰는 비교(임베딩 모델, 구간 규칙 등)는 이 잡음이 없습니다.
5. 설명문을 묶음 크기와 상관없이 똑같이 만들려면 vision 부분을 float32로 돌려야 합니다(혼자 vs 묶음 차이 0.001%). 속도·메모리 비용이 있어 이번에는 적용하지 않았습니다.
