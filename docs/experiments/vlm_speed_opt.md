# Qwen3-VL-Embedding-2B 프레임 특징 추출 속도 최적화 (2026-11-11)

판정 기준의 시간 한도(특징 추출 ≤ 영상 1분당 1.5초, [vlm_model_plan.md](vlm_model_plan.md) 5절)는 바꾸지 않고 최적화만 했습니다. dev 영상 8개(55분 24초, 2초마다 프레임 1장, 1,659장), 640×360 입력, RTX A5000에서 쟀습니다.

스크립트: [speed_opt.py](../../ai/experiments/vlm_model/speed_opt.py), 결과: [speed_opt.json](../../ai/experiments/vlm_model/results/speed_opt.json)

## 결과

단위: 영상 1분당 초. 「같은 결과?」는 처음 설정(base)으로 만든 특징과의 코사인 유사도(평균 / 최소)입니다.

| 단계 | 설정 | 프레임 읽기 | 전처리 | 모델 계산 | **합계** | 기준 대비 | GPU 최대 | 같은 결과? |
|---|---|---|---|---|---|---|---|---|
| 처음 | CPU 디코딩, 전처리 CPU(torchvision), 묶음 8 | 0.48 | 0.51 | 0.84 | **1.83** | – | 4.40 GiB | 1.000 / 1.000 |
| 1) 전처리 GPU | 프레임을 uint8 텐서로 GPU에 올려 전처리 | 0.50 | 0.03 | 0.86 | **1.39** | −24% | 4.41 GiB | 0.998 / 0.989 |
| 2) GPU 디코딩 | + NVDEC 디코딩·축소 (`h264_cuvid`, `scale_cuda`) | 1.21 | 0.03 | 0.86 | 2.10 | +15% | 4.41 GiB | 0.979 / 0.859 |
| 3) 묶음 크기 | GPU 디코딩 + 묶음 16 / 32 | 1.13 | 0.02 | 0.84 / 0.82 | 1.99 / 1.97 | +9% / +7% | 4.83 / 5.68 GiB | 0.979 / 0.859 |
| 3') 묶음 크기 | CPU 디코딩 + 전처리 GPU + 묶음 16 / 32 | 0.44 / 0.41 | 0.03 / 0.02 | 0.84 / 0.83 | **1.31 / 1.26** | −29% / −31% | 4.84 / 5.69 GiB | 0.998 / 0.989 |
| 4) 추가: 겹치기 | 3') 묶음 16 + 다음 영상 디코딩을 지금 영상 계산과 동시에 | (0.42) | (0.03) | (0.85) | **0.96** (실제 걸린 시간) | −47% | 4.84 GiB | 0.998 / 0.989 |

- 「기준 대비」는 처음 설정(1.83초)과 비교한 것입니다. 1)~3)은 앞 단계 설정에 하나씩 더한 것이고, 3')은 2)를 빼고 1)에 묶음 크기만 바꾼 것입니다.
- 처음 설정의 기본 이미지 전처리는 이미 빠른 프로세서(torchvision 백엔드)였습니다. 느린 PIL 프로세서는 이 transformers 버전에서 영상 프로세서 때문에 불러올 수 없어 비교하지 못했습니다.
- 4)의 겹치기는 여러 영상을 연달아 처리할 때의 실제 걸린 시간(wall)입니다. 프레임 읽기·전처리·계산 칸은 각 단계 시간을 더한 값이라 합계보다 큽니다.

## 해석

1. **전처리를 GPU로 옮긴 것만으로 한도 안에 들어왔습니다**(1.83 → 1.39초). 전처리 시간이 0.51 → 0.03초가 됐습니다. 결과는 거의 같지만 완전히 같지는 않습니다(코사인 평균 0.998, 최소 0.989). GPU와 CPU의 리사이즈 보간 계산 차이로 보입니다.
2. **GPU 디코딩은 오히려 느렸고(0.50 → 1.21초), 결과도 달라졌습니다**(최소 0.859). 2초에 1장만 뽑는 경우에는 NVDEC가 모든 프레임을 디코딩해 GPU에서 내려받는 비용이 더 큰 것으로 보입니다. 결과가 달라진 원인은 `scale_cuda`의 축소 방식과 색 변환 차이로 추정하고, 따로 확인하지 않았습니다. 채택하지 않습니다.
3. 묶음 크기는 모델 계산을 조금만 줄였습니다(0.86 → 0.84 → 0.83초). 묶음 32는 묶음 16보다 0.05초 빠르지만 GPU를 0.85 GiB 더 씁니다.
4. 디코딩(CPU)과 계산(GPU)을 겹치면 0.96초까지 줄어듭니다. 지금은 여러 영상을 이어서 처리할 때만 효과가 있고, 영상 하나 안에서도 겹치려면 디코딩을 조각내서 흘려 보내도록 바꿔야 합니다.

## 채택

- **CPU 디코딩 + 전처리 GPU + 묶음 16** (영상 1분당 1.31초, GPU 4.84 GiB). 판정 기준의 시간 한도(1.5초) 안입니다.
- [extract_eval_features.py](../../ai/experiments/vlm_model/extract_eval_features.py)를 이 설정으로 바꾸고, dev 특징을 다시 뽑았습니다. 다시 뽑은 실제 시간은 영상 1분당 640×360 **1.32초**, 1280×720(참고) 4.06초입니다. 처음 설정으로 뽑은 특징은 `eval_features/qwen_640_v0`, `qwen_1280_v0`에 남겨 두었습니다(속도 비교의 기준).
- 서비스에 연결할 때 겹치기(4)를 넣으면 더 줄일 수 있습니다. 판정에는 채택 설정의 값(1.31~1.32초)을 씁니다.
